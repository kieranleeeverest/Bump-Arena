# 联机同步与性能优化实录（2026-11-26 凌晨）

> 记录一次从"每 50ms 广播全量球位"到"出杆事件 + 各端本地确定性推演 + 按需兜底轨迹"的改造，
> 以及随后把物理里两处 O(球 × 221 段) 的边界循环换成网格索引的过程。
> 文中所有数字都是本机 headless 实测或手机端 `?diag=1` 角标读数，不是估算。

---

## 0. 一句话结果

| 指标 | 改造前 | 改造后 |
|---|---|---|
| 手机端帧率（中端机，1.5×） | 14 – 21 fps | **58 fps** |
| 最长帧 | 58 – 67 ms | **25 ms** |
| 物理脚本 `phys` | 16.7 ms | **8.3 ms** |
| 每帧绘制调用 `dc` | 92 – 96 | 60 – 96（本来就不高） |
| 正常对局轨迹流量 | 每杆约 21 KB | **0 字节**（按需订阅） |
| pck 体积 | 7.42 MB | **4.73 MB** |
| 首屏（wasm br + pck br） | 约 13.4 MB | **约 11.3 MB** |
| 出杆到球动（出杆方） | 约 200 ms | **0** |

## 1. 起点：三个同时存在的问题

1. **杆末整盘球跳一下**（球多、碰撞多时明显，球少看不出来）。
2. **出杆前半程不跟手**：松手到球动有约 200 ms 空档。
3. **掉帧**：中端机 14 – 21 fps，最长帧 58 – 67 ms。

旧架构是"宿主 20 Hz 广播全量球位（约 400 B/次）+ 客户端插值追赶宿主时钟"。
带宽和客户端 CPU 都随"帧数 × 球数"线性涨，而台球真正需要高频同步的只有球在动的那几秒。

## 2. 阶段一：一杆一轨迹（先修"杆末跳"）

### 2.1 做法

宿主在出杆瞬间录第 0 帧（杆前静止状态），此后每个物理帧录一帧，每 100 ms 推一段；
客户端攒一小段后按 **1.0 倍速本地播放**，不再追宿主时钟。

二进制包格式见 `prototype/scripts/network/ShotTrajectory.gd`：

```
包头 17 B：magic 'T' / version / shot_id / shot_start_ms / first_frame / frame_count / ball_count / frame_ms
每帧 4 B + 每球 6 B：mask / dead / (x*8, y*8, angle)
```

`frame_ms` 随包下发（而不是写死 1/60），物理帧率以后调整不会让播放速度错。

### 2.2 关键取舍

**没有做"位置没变就不发"的省流版本。** 做过一版，但轨迹是分段下发的，客户端在段首
没有"上一帧"可以继承，静止球会瞬移到 `(0,0)`。一帧 9 球也才 58 字节，不值得为这点流量
换一类定位不到的抖动。

### 2.3 结果与局限

杆末不跳了，观战/对手顺滑了。但出杆方仍然要等服务端算完再回放，约 200 ms 延迟。

## 3. 阶段二：出杆方本地预演（修"不跟手"）

### 3.1 为什么敢在手机上重跑物理

`step()` 里**没有随机数、不刷新道具球、不推进回合**，输入只有"初态 + pull + 固定步长 1/60"。
所以松手瞬间用同一份代码在本地开跑，理论上逐帧可复现。

### 3.2 核心教训：台球是混沌系统，初值差一点就会炸

第一次上线后：出杆方零延迟了，但**杆末整盘球跳一下**，而且"多球位移才跳、球少不跳"。

同机对拍（两个 `main.tscn` 实例，一个走权威出杆路径、一个走预演路径，逐帧比位置）：

| 初值精度 | 414 帧后整盘最大偏差 |
|---|---|
| 快照 `snappedf(p, 0.01)` | **16.32 px** |
| 精确原值 | **0.0000 px** |

**根因**：状态快照把球坐标量化到 0.01 px，客户端从这个初值积分，误差被碰撞不断放大
（约 2400 倍）。球越多、碰撞越多，放大越狠——正好对上"多球才跳"的现象。

**修法**：`make_network_snapshot()` 里球的 `p` / `v` 不再 `snappedf`，直接发原值。
Godot 的 JSON 对 float 是无损往返的（13–17 位有效数字，能精确还原 float32）。
代价：每个快照多约 150 字节。

### 3.3 试错记录：为什么"逐帧用权威轨迹校正"是错的

先试过另一条路：预演期间收下权威轨迹帧，每帧把误差按 40% 拉回。
实测**更糟**：

| 权威帧延迟 | 最终偏差 |
|---|---|
| 0 帧 | 0.247 px |
| 6 帧（≈ 100 ms） | 10.4 px |
| 12 帧（≈ 200 ms） | 17.5 px |

原因：权威帧永远比本地慢半拍，拿"旧帧的误差"去修"当前的位置"等于注入滞后。
**这条路已删除，别再走。**

### 3.4 正确做法

只保证初值逐位一致，不做任何中途校正；`rest` 到达时对账一次（正常偏差 < 0.5 px，
日志会打 `PREDICT_END drift=0.000px`）。

被服务端拒绝（`no_seat` / `not_owner` / `stale_turn`）或包没发出去时，回滚到出杆前状态，
并给出明确文案——不伪装成功。

### 3.5 顺手补的三个"看得见的缺口"

预演只做了物理，出杆的**非物理副作用**（双倍消耗、副塔技能充能、吸血球归属）要等 `rest`
才更新，杆进行中技能条不涨。已抽出 `_apply_shot_bookkeeping()`，权威与预演都调用，
幂等、`rest` 会覆盖，`shot_number` 仍只由权威推进。

## 4. 阶段三：shot 事件广播 + 全员预演 + 按需轨迹

### 4.1 出杆事件

宿主接杆后广播 `shot_event`（`slot` + **原值 pull** + `nonce`，约 90 字节，排除出杆方）。
其他人收到就在本地开跑，从"等 200 ms 回放"变成零延迟；观战者也参与（出杆权限仍由
`can_control_current_ball` 拦截，观众不会误触）。

**三方必须用完全相同的 pull**：宿主把收到的原值再广播出去，出杆方本地用的也是同一个
float32——否则又回到 3.2 的混沌放大。

### 4.2 轨迹改成按需订阅

全员预演之后，轨迹流变成纯兜底。现在宿主**每杆开始时清零 `traj_want`**，只有这几类客户端会订阅：

- 中途加入（`hello` 时若在杆中途，自动订这一杆）
- 预演起不来（还在播上一杆 / 回合对不上 / 观战席状态不新）
- 收到"球在动"的快照但本地既没预演也没收到轨迹帧（`trajectory_needed` 信号，500 ms 节流）

正常对局一杆的轨迹字节是 **0**，宿主日志会给证据：
`TRAJ shot=7 frames=414 dur_ms=6900 subs=0 bytes_total=0`。

## 5. 阶段四：物理热点（真正吃掉帧率的地方）

### 5.1 先量化，别猜

手机端 `?diag=1` 读数（默认 1.5×）：

```
dc 92  proc 16.97  phys 22  draw 0.68  hud 0.76
```

`dc 92`（每帧 92 次绘制调用）、`draw 0.68 ms`、`hud 0.76 ms` —— **渲染侧轻得离谱**。
`proc` 与 `phys` 几乎相等，说明空闲脚本几乎为 0，**全部成本在物理**。

### 5.2 找到两处 O(球 × 221 段)

`boundary_outline` 有 **221 段**，两个函数每次都要遍历整条轮廓：

| 函数 | 原实现 | 单次耗时（本机） |
|---|---|---|
| `_sweep_boundary` | 每段算一次 `normalized()`（带 sqrt） | **31.8 µs** |
| `_resolve_boundary_overlap` | 每段 × 3 遍，同样带 `normalized()` | 真正的大头 |

按 7 球 × 4 子步算，一个物理帧里就是上万次段测试和上千次开方。

### 5.3 改法

1. **预计算**：段起点 / 边向量 / 内法线 / 长度平方 / AABB，全部存进扁平 `PackedVector2Array`
   （躲开 GDScript 的 Dictionary 取值——实测 221 次字典取值本身就要 31 µs）；
2. **网格索引**：按 64 px 建 `Vector2i → 段索引数组`，查询时只取覆盖到的那几格（通常 1–4 格）；
3. **重合判定**用小球 AABB 查询，**扫掠判定**用"路径胶囊 AABB"查询，两者都能保证不漏段
   （任何可能命中的段，其 AABB 必然与查询盒相交）。

### 5.4 结果（本机 headless 实测）

| 指标 | 改前 | 改后 |
|---|---|---|
| `_sweep_boundary` 单次 | 31.8 µs | **0.8 µs**（40×） |
| `step()` 单次 | 496 µs | **61 µs**（8×） |
| 一个物理帧（4 子步） | 1985 µs | **244 µs** |

手机端 `phys` 从 **16.73 ms 降到 8.26 ms**，帧率从 14–21 回到 **58**，最长帧 67 → 25 ms。

### 5.5 正确性验证

纯几何/数据结构改造，物理结果应完全等价。验证方式：5 杆全速撞墙（含斜角、贴角），
每子步检查每颗球是否仍在轮廓内——**0 次穿出边界**。

## 6. 渲染层：被数据否决的一层

原方案里的"静态层缓存 + 脏区重绘"**没有做**，理由是数据不支持：

- `dc` 只有 60–96（每帧绘制调用数）
- `draw` 0.68–1.67 ms（棋盘 `_draw`）
- `hud` 0.72–1.75 ms（HUD `_draw`）
- 中文文本只有 7 处 `draw_string`

另外要纠正一个概念：**Godot 2D 没有像素级"脏矩形"**。`queue_redraw()` 是该 CanvasItem
命令全量重发，不是局部重绘。真正的收益只能来自"把静态内容烘焙成一张贴图"，
而在 `dc` 已经 60 的前提下，这笔改造收益接近零、还要冒改视觉的风险。

**结论：这一层不做。** 如果要再压，只有减 overdraw（大面积半透明叠加）或降 DPR，都不是"免费"的。

## 7. 首屏体积：pck 7.42 MB → 4.73 MB

导出预设原来是 `export_filter="all_resources"`，把一堆只在开发时用的东西打进了包：

| 排除项 | 内容 | 体积 |
|---|---|---|
| `assets/ui/pwa/*` | PWA 图标源图（含一张 1.1 MB 的重复源文件） | ~2.6 MB |
| `tests/*` | 39 个测试脚本（导出日志里 78 条） | ~0.3 MB |
| `test_*.gd*` / `capture_*.gd*` / `probe*.gd*` | 根目录 15 个调试脚本 | 小 |

修改 `prototype/export_presets.cfg`：

```
exclude_filter="assets/arena/arena_celestial*.png,assets/ui/pwa/*,tests/*,test_*.gd*,capture_*.gd*,probe*.gd*"
```

**验证**：导出后 `index.144x144.png` / `index.512x512.png` 仍在构建根目录（PWA 图标由导出器
从源文件生成，不依赖 pck）；`app_shell.tscn`、`main.tscn`、`PrototypeMatch.gdc`、
`AppShellPrototypeV1.gdc`、`arena_nebula_crystal_final.png` 仍在包内。

| 指标 | 改前 | 改后 |
|---|---|---|
| pck 原始 | 7,416,476 B | **4,727,168 B**（−36%） |
| pck brotli | ~5.6 MB | **3.45 MB** |
| 首屏合计 | ~13.4 MB | **~11.3 MB** |

> 顺带发现 `assets/ui_preview/`（428 KB）在脚本和场景里都没有引用，疑似死资源，
> 尚未排除——需要先确认没有动态 `load()` 路径。

## 8. 观测：四个数 + 三个分项

### 8.1 手机端 `?diag=1` 角标

```
FPS 58  p95 25ms  >50 0
frame max 25ms
canvas 540x1064   DPR 3.00   win 390x768
net n=0 lag=-1 buf=110 jit=0
dc 60 proc 18.27 phys 8.26 draw 1.67 hud 1.75
```

判读：

| 现象 | 结论 |
|---|---|
| `dc` 高且 `draw` 高 | 命令太多 → 烘焙静态层 |
| `dc` 低但 `p95` 高 | 填充率不够 → 减 overdraw / 降 DPR |
| `phys` 高 | 物理热点 → 查 `step()` |
| `proc - phys` 高且 `draw/hud` 低 | 空闲脚本 → 查 `_process` |
| `n=0 / lag=-1` | 预演期间正常（样本被清空），不是异常 |

### 8.2 服务端

宿主每 10 秒一条 `NET_RATE in_flight=4 bytes/s=... total=...`，用于判断"卡在网络还是渲染"。

### 8.3 测量工具本身会污染测量

`arenaPerf` 的大 JSON 每 500 ms 序列化 + `JavaScriptBridge.eval` 一次，约 3.4% 的帧会被它
拖长，足以把 `p95` 从 17 ms 顶到 25 ms。已把它降到 **2 秒一次**；角标读的 `arenaNetDiag`
（6 个标量）保持 500 ms。

角标的帧缓冲也从"每帧 `shift()` 一个 4000 元素数组 + 每 500 ms 排序 4000 个"改成了
**600 元素环形缓冲**。

## 9. 踩坑清单

| # | 坑 | 教训 |
|---|---|---|
| 1 | 轨迹做"位置没变就不发"的省流 | 分段下发时客户端没有段首继承，静止球瞬移 (0,0) |
| 2 | 只发 0.01 px 精度的初值 | 混沌放大 2400 倍，杆末整盘跳 16 px |
| 3 | 用滞后的权威帧逐帧校正 | 等于注入滞后，延迟越大越糟（12 帧 → 17.5 px） |
| 4 | 把 `exclude_filter` 想成"只是不导出" | 要验证 PWA 图标仍生成、关键场景仍在包内 |
| 5 | 用 3× 全分辨率的截图判断性能 | 224 万像素是 1.5× 的 4 倍，只能说明"极限档扛不住" |
| 6 | 只看 `p95` 不看口径 | p95 是长窗口、FPS 是 500 ms 窗口，两者可以同时"看起来矛盾" |
| 7 | 以为 `net n=0 lag=-1` 是网络异常 | 预演期样本被清空，属正常 |
| 8 | `scp` 传 7 MB pck 到香港偶发断连 | 脚本自带 3 次重试，连续失败就再跑一次脚本 |

## 10. 已知限制与下一步

**限制**

- 对手/观战的"出杆"延迟仍是一个 RTT（击球端 → 服务器 → 对手），这是因果下限，
  任何带宽优化都消不掉。
- 观测者不参与预演时走回放（200 ms），这是兜底路径，不是 bug。
- 杆进行中的状态包仍是 5 Hz（约 2 KB/s）。**不建议再降**：一杆只省 10 KB（≈ 0.006 元），
  而它是兜底人群的血条来源和 `rest` 之前的中间校正点。

**下一步（按收益排序）**

1. 四人 / 观战容量实测——P1-05 那套基线是旧版 20 Hz 广播测的，流量结构已完全改变，旧数字作废。
2. `assets/ui_preview/` 等死资源确认后排除。
3. `step()` 再压 20–30%（把 `b.p` / `b.v` 的字典取值改成局部变量缓存）。
   **收益**是给低端机留余量；**代价**是动核心物理、写回漏一个字段就会静默改变球的行为，
   且回归面（球-球、球-塔、穿墙、伤害）比边界那两处大得多。当前 58 fps 已达标，建议缓做。
