# 物理热点与并行数组迁移清单（2026-11-26）

> 这份文档不是"现在就要做"的工单，而是"一旦弱机 phys 抬头就能直接动手"的施工图。
> 所有数字都是本机 headless 实测或 Chrome CPU 节流实测。

---

## 0. 先看结论：优先级已经被实测翻转

`tools/perf_web_ab.js` 三档对照（同一构建、同一台桌面、CPU 节流模拟弱机）：

| 配置 | canvas | fps | p95 | max | >50 帧 | `proc` | `board` | **`hud`** |
|---|---|---|---|---|---|---|---|---|
| default（无节流） | 585×1266 | **60** | 17.0 | 33.0 | 0 | 14.3 ms | 480 µs | **1205 µs** |
| cpu6（6× 节流） | 585×1266 | **24** | 83.0 | 167.0 | 257 | 48.8 ms | 435 µs | **8910 µs** |
| cpu6_lowres（6× + 1×） | 390×844 | **39** | 83.0 | 183.0 | 92 | 52.5 ms | 7325 µs | **2710 µs** |

**三点结论**：

1. 只有 `default` 是 60 fps——**一加 8T 的 58 fps 确实是幸存者偏差**，6× 节流（≈弱机）直接掉到 24 fps。
2. `cpu6_lowres` 只回到 39 fps：**降分辨率救不了 CPU 瓶颈**，这条再一次否掉"渲染/填充率"方向。
3. `hud` 从 1.2 ms 涨到 **8.9 ms（≈7 倍）**，而 `board` 基本不动（480 → 435 µs）。
   **弱机上最大的单项不是物理，是 HUD 绘制。**

所以真要给弱机做优化，顺序应该是：

| 优先级 | 项 | 依据 |
|---|---|---|
| 1 | **HUD 绘制**（文本 shaping / 圆角面板 / ink glass） | 弱机上 8.9 ms，是 `board` 的 20 倍 |
| 2 | 物理并行数组 | 本机 61 µs/步，弱机上按 7× 估约 0.4 ms/步 × 4 = 1.7 ms/帧 |
| 3 | 再压渲染 | `dc` 60~122、`board` < 0.5 ms，收益最小 |

**换句话说：本文档描述的并行数组改造，在弱机上大概只能拿回 1.5–2 ms/帧；先把 HUD 那 8.9 ms 削掉才是正解。**

## 1. 现状（本机 headless，7 球，无洞）

| 指标 | 值 |
|---|---|
| `boundary_outline` | 221 段 |
| `_sweep_boundary` 单次 | 0.8 µs（网格化后；原来 31.8 µs） |
| `_resolve_boundary_overlap` | 网格化后已不是热点 |
| `step()` 单次 | **61 µs** |
| 一个物理帧（4 子步） | **244 µs** |

四段的划分（代码里有 `段 1/4` ~ `段 4/4` 标记）：

| 段 | 内容 | 复杂度 |
|---|---|---|
| 1/4 | 球-洞 + 积分（唯一推进 `p` 的地方，含火球烧洞、吞噬） | 球 × 洞（≤9×3） |
| 2/4 | 球-球 | **O(n²)**：7 球 21 对，9 球 **36 对** |
| 3/4 | 球-塔（道具球消耗、伤害、技能打断） | 球 × 塔（9×6） |
| 4/4 | 边界（网格索引） | 每球 1~4 格，约 10 段 |

**注意第 2 段是超线性的**：球数从 7 到 9（+29%），碰撞对从 21 到 36（**+71%**）。
所以"4 人局客户端 phys 会比 1v1 高 30–70%"，不是线性增长。

## 2. `balls` 元素结构与热路径字段

每个球是 `Dictionary`，由 `_ball(kind, slot, position)` 创建：

```
kind / id / p / v / r / alive / armed / hp / angle / spin / spin_kick / impact / owner_side / spawn_team
运行期追加：self_hit_latch{} / damage_latch{}（球-塔去重）
```

**真正进热路径的只有这些**（`step()` 里读写）：

| 字段 | 读 | 写 | 备注 |
|---|---|---|---|
| `p` | ✓ | ✓ | 段 1 积分；段 2/3 碰撞修正；段 4 重叠修正 |
| `v` | ✓ | ✓ | 段 1 阻尼；段 2/3 反弹；段 4 反弹 |
| `r` | ✓ | — | 半径（恒为 `BALL_RADIUS`，但保留字段） |
| `alive` | ✓ | ✓ | 洞/伤害/道具球消耗 |
| `kind` | ✓ | — | 决定火球烧洞、吸血、伤害归属 |
| `hp` | ✓ | ✓ | 玩家球被塔击穿 |
| `armed` | ✓ | ✓ | 球-球碰撞后置 true（决定塔伤害是否生效） |
| `impact` | ✓ | ✓ | 仅表现（渲染脉冲），不影响物理 |
| `spin` / `spin_kick` | ✓ | ✓ | 仅表现（滚动视觉） |
| `owner_side` | ✓ | — | 仅吸血球结算 |
| `self_hit_latch` / `damage_latch` | ✓ | ✓ | 球-塔去重，离开塔后清除 |

> **`angle` 不在 `step()` 里**：它由 `_update_orb_visuals(dt)` 推进，属于表现层。
> 这是切并行数组时最容易漏掉的一点——`angle` 不该进物理数组。

## 3. 什么时候才动（触发条件）

**不要因为"看起来还能优化"就动。** 满足任一条件再做：

1. 弱机（6× 节流等效）实测 `phys` > 4 ms；
2. 4 人局（9 球）实测 `phys` 比 1v1 高出 70% 以上，且帧率跌破 55；
3. 出现"球在动时掉帧、球静止时流畅"的可复现案例，且 `board`/`hud` 都不高。

如果只是 `hud` 高、`phys` 正常——**去改 HUD，别碰物理**（见第 0 节）。

## 4. 迁移清单（切并行数组）

目标：把 `Array[Dictionary]` 换成并行数组，消除每个子步上千次的字典装箱/取值。

```
bp:  PackedVector2Array   # 位置
bv:  PackedVector2Array   # 速度
br:  PackedFloat32Array   # 半径
balive: PackedByteArray   # 0/1
bkind: Array[String]      # 球种（低频访问，保持字符串）
bhp: PackedInt32Array
barmed: PackedByteArray
bimpact / bspin / bspin_kick: PackedFloat32Array
bowner: PackedInt32Array
```

**需要改的函数（按改动量排序）**：

| 函数 | 改什么 |
|---|---|
| `step()` 段 1/4 | `b.p += b.v * dt` → `bp[i] += bv[i] * dt`；洞判定读 `bp[i]` |
| `step()` 段 2/4 | 局部变量取 `bi`/`bj`，碰撞解算后写回 `bp`/`bv`/`bspin` |
| `step()` 段 3/4 | 传索引而不是 Dictionary 给 `_apply_tower_damage` |
| `step()` 段 4/4 | `_sweep_boundary(origin, travel, r)` 已经是标量入参，只需调整调用处 |
| `_resolve_boundary_overlap(i)` | 入参从 `Dictionary` 改为索引 |
| `_collide_field_walls()` | 同上 |
| `_apply_tower_damage(i, tower_index, …)` | 入参从 `Dictionary` 改为索引 |
| `_update_orb_visuals(dt)` | **不迁移**，继续读 `angle`/`spin`（表现层） |
| `make_network_snapshot()` / `apply_network_snapshot()` | 只改取值方式，JSON 结构不变 |
| `apply_trajectory_chunk()` / `_apply_replay_frame()` | 同上 |

**不建议的做法**：加一层 `BallStore.get_pos(i)` 之类的访问器——GDScript 的函数调用开销会把
省下来的字典取值又吃回去，实测会净亏 30%。

---

## 5. 收益与代价

**收益**：`step()` 61 µs → 约 45 µs（−25%）；按弱机 7× 折算，每帧省 **1.5–2 ms**。

**代价**：

1. 动的是核心物理，写回漏一个字段不会报错，只会改变球的行为；
2. 回归面覆盖：球-球碰撞、球-塔伤害、道具球消耗、副塔技能打断、吸血球、穿墙、洞吞噬；
3. 可维护性下降：`p`/`v`/`hp`/`armed` 都要"读—算—写回"三件套。

**所以：只有在第 3 节的条件成立时才做。** 现在的 61 µs 不是问题，HUD 的 8.9 ms 才是。

## 6. 验证清单（改完必须逐条过）

1. **穿墙**：5 杆全速打向不同角度，每子步检查球是否仍在 `boundary_outline` 内，`escapes == 0`；
2. **球-球**：两球正碰后速度交换、斜碰后分离方向正确；
3. **塔伤害**：`self_hit_latch` 生效（同一颗球反复撞同一座塔只扣一次）；
4. **道具球**：火球撞塔即消失并造成双倍伤害；吸血球按 `owner_side` 治疗己方；
5. **预演一致性**：同一杆在"权威路径"和"客户端预演路径"下跑完，终态偏差 < 0.5 px
   （日志 `PREDICT_END drift=`）。

前 4 项可用 `prototype/tests/` 下的现有脚本，第 5 项需要临时对拍脚本（见
`docs/联机同步与性能优化实录-20261126.md` 第 3.2 节的写法）。

## 7. 附：HUD 绘制已按第 0 节的结论修完（2026-11-26）

做法（不改任何视觉）：

1. **静态层改成"内容签名驱动"**：头像/昵称/血条/计时/观战条只在"血量、存活、轮次、墨水比例、双倍/眩晕、观战人数"变化时才 `queue_redraw()`，不再无条件 30Hz 重画；
2. **浮动文字拆到独立子 CanvasItem**：它是唯一需要 30Hz 的东西，单独每帧画；最后一个浮字消失时额外重画一帧，避免残影。

同一套 cpu6（6× CPU 节流）对照：

| 指标 | 改前 | 改后 |
|---|---|---|
| fps | 24 | **39** |
| p95 | 83 ms | **67 ms** |
| max | 167 ms | **100 ms** |
| `>50` 帧 | 257 | **82** |
| **`hud`** | **8910 µs** | **1295 µs（6.9×）** |
| `proc` | 48.8 ms | **31.9 ms** |

`hud` 落到 1.3 ms 之后，弱机上的头号成本已经不是 HUD，也不是 `board`（715 µs）——
下一步要重新量一次分项，不要凭上一轮的结论继续追。

## 8. 三个后续候选的判定（2026-11-26，全部未采纳）

| 候选 | 数据 | 判定 |
|---|---|---|
| `phys` 并行数组 | `phys_ms 9.22`（cpu6），但 `solo_net` 在同一进程里同时跑权威实例 + 预演，**约放大 2 倍**；真实客户端约 4.6 ms | 不做：净收益约 1 ms，代价是动核心物理 |
| 绘制命令合并（弧段数） | `prim 4954`，主因是 6 座塔的抗锯齿弧（36/44 段）；把满杯环降到 24 段后**测不出差异** | 不做：无法验证的改动不发布 |
| 音频（voices/解码） | `voices` 长期 0–1 | 不做：不是瓶颈 |

### 关键教训：这个 harness 在 6× 节流下的噪声接近 2 倍

同一个构建连跑两次（`--only=cpu6 --shots=4`）：

| 指标 | 第 1 次 | 第 2 次 |
|---|---|---|
| fps | 26 | 49 |
| p50 | 33 ms | 17 ms |
| `hud` | 4025 µs | 9400 µs |

**结论**：`cpu6` 档只能用来判断"数量级"（24 → 50+ 这种），分辨不了 20–30% 的改进。
要拿它做精细 A/B，必须先：固定 CPU 频率、关掉后台、同一构建跑 5 次取中位数。

**因此帧率调优到此为止。** 再往下调，测出来的差异都不比噪声大。
